# libSceJpegDec technical debt

### Functional

- [libSceJpegDec](../../../core/libs/prx/libSceJpegDec/Export.cpp) returns SCE_JPEG_DEC_ERROR_INVALID_ADDR for unmapped or unwritable pointer arguments, buffers and input-callback chunks and SCE_JPEG_DEC_ERROR_INVALID_HANDLE for an unreadable handle. This is a defensive host-protection fallback; console behaviour for unmapped or read-only memory is unmeasured.
- [libSceJpegDec](../../../core/libs/prx/libSceJpegDec/Export.cpp): work-memory size, alignment, creation checks, image-info fields, progressive coefficient-buffer capacity, row-buffer capacity and scaled dimensions are recovered from the native module. The host still allocates its decoder storage separately rather than using the guest work and coefficient regions. Malformed-header diagnostics and output mutation on failure are not fully matched.
- [sceJpegDecDecode](../../../core/libs/prx/libSceJpegDec/Export.cpp): decode mode 1 and pixel formats 9 and 10 throw (incomplete in shadPS4). Y8 follows [shadPS4](https://github.com/shadps4-emu/shadPS4/blob/33e73127119f672f9f08b8a5a7f71600263f61d9/src/core/libraries/jpeg/jpegdec.cpp#L267-L317): rows are one byte per pixel, each `(77R + 150G + 29B) >> 8` of the decoded, clamped RGB. For a colour source this is luma re-derived from RGB, not the decoded Y component; the two differ by rounding and wherever the YCbCr to RGB step clips. One title (PPSA29866) disassembled for this entry has one call site (0x2c111d); it passes a null `imageInfo` and a parameter structure with decode mode 0, down-scale 1 and pixel format 0, and hands the result to another function whose handling of a negative result was not read. In the parameter structure built around this call site, mode 1 and formats 9, 10 and 11 do not show up; whether a down-scale of 1 means no scaling was not compared.
- [sceJpegDecDecode](../../../core/libs/prx/libSceJpegDec/Export.cpp) pixel values: a PS5 payload process (firmware 11.60) decoded a 16x16 grayscale JPEG with values 1 away from this decoder's at 4 of the 16 pixels of a row (`0x0f`, `0x61`, `0x8f` and `0xe1` where this one gives `0x10`, `0x60`, `0x90` and `0xe0`), and a 16x16 colour JPEG with RGB channels up to 2 away. Its Y8 output for that colour image equals `round(0.299R + 0.587G + 0.114B)` of its own RGB at the 8 pixels of a row where both were read, while `(77R + 150G + 29B) >> 8` gives 1 less for the green ones; it does not show whether the console takes the decoded Y component instead. The decoders are not bit-exact, and neither is shown to be the more accurate one; a title process was not measured.
- [sceJpegDecDecodeWithInputControl](../../../core/libs/prx/libSceJpegDec/Export.cpp) (libSceJpegDec): decode mode 1, pixel formats 9 and 10, unlisted parse down scale, decoding without parse and decoding at another down scale throw. Y8 follows the entry above; PS5 unmeasured. A stream that ends before the frame header, or cannot form one, returns 0x80650012 (measured on PS5 firmware 13.42 libSceJpegDec.sprx; sceJpegDecParseHeader on the same bytes returns 0x80650010 or 0x80650002); callback call counts differ because the firmware (13.60 disassembly) refills its 2 KiB buffer when under 0x3F0 bytes remain, whereas this implementation pulls in 2048-byte blocks. Streamed bytes reside in host memory; freeing work memory without `sceJpegDecDelete` leaves them allocated. A call reaching a stream another call on the handle is still reading (a decode from its own input callback) throws; the console's answer is unknown. A delete or new parse during a call leaves it reading its own stream.
